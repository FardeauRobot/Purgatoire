## Finding 1 — Affichage des résultats en précision par défaut (6 chiffres significatifs, notation scientifique)   [POLISH]

### What went wrong
`std::cout << value * it->second` utilise la précision par défaut du flux, soit 6 chiffres significatifs. Dès que le résultat dépasse 6 chiffres, il est arrondi, puis passe en notation scientifique :
```
2022-03-29 => 1000 = 4.71159e+07      (valeur exacte : 47115930)
9999-12-31 => 1 = 47115.9             (taux dans data.csv : 47115.93)
2011-01-03 => 1e-07 = 3e-08
```
La grille dit : *« Please compare some dates manually with the specified value. »* Le résultat est juste à 6 chiffres près, mais `4.71159e+07` fait tiquer à la comparaison manuelle. L'exemple du sujet utilise lui-même le format par défaut (`= 0.36`, `= 7.1`), donc ce n'est pas une faute, juste une question probable.

### Where
`BitcoinExchange.cpp:137`

### How to fix
Le format par défaut, c'est ce que fait `%g` en C. Il faut savoir le justifier en défense. `std::fixed` casse la sortie du sujet (`0.900000`). Augmenter `std::setprecision` (de `<iomanip>`) **sans** `std::fixed` fonctionne, et c'est mesuré sur une copie hors arbre avec `setprecision(15)` : la sortie du sujet reste identique (`0.9`, `0.36`, `0.32`, `7.1`), et on obtient `1000 = 47115930` et `1 = 47115.93`. Les précisions 10 et 12 donnent le même résultat. À 17, ça casse : on voit `0.89999999999999991`, c'est-à-dire le bruit binaire du `double`.

### How to spot it next time
Teste les **extrêmes du domaine de sortie**, pas seulement ceux de l'entrée. La valeur max (1000) × le taux max (dernière ligne de `data.csv`) donne le plus grand nombre que le programme peut afficher. Lance cette ligne et regarde s'il y a un `e+` dans la sortie. Pense à `printf("%g")` : dès que tu affiches un `double` sans manipulateur, c'est ce format-là que tu obtiens.

## Finding 2 — Codes couleur ANSI dans les messages d'erreur, et choix du flux   [POLISH]

### What went wrong
Le sujet affiche `Error: bad input => 2001-42-42`. Ton programme émet `\033[1;31mError: \033[0mbad input => 2001-42-42`, ce qui s'affiche bien dans un terminal. En revanche, si l'évaluateur redirige vers un fichier ou fait un `diff` avec la sortie attendue, les octets ne correspondent pas (`cat -v` montre `^[[1;31mError: ^[[0m...`).

Sur le flux, il y a une tension à connaître. Le chapitre II dit : *« Unless specified otherwise, every output message must end with a newline character and be displayed to the standard output. »* L'ex00 dit seulement : *« Your program should display on the standard output the result… »*. Tes erreurs partent sur `std::cerr`. C'est la convention et la plupart des évaluateurs l'acceptent, mais une lecture littérale du chapitre II pourrait contester. Ce n'est pas une case de la grille.

### Where
`errors.cpp:8` (couleurs) ; `errors.cpp:8` + `BitcoinExchange.cpp:117,121,125,133` (stderr)

### How to fix
Enlève les couleurs du préfixe `Error: ` dans ce projet, ou garde-les en sachant le défendre. Pour le flux, prépare une phrase : « les résultats vont sur stdout comme le demande l'ex00, les erreurs sur stderr pour qu'on puisse filtrer avec `2>/dev/null` ».

### How to spot it next time
Passe toujours la sortie par `| cat -v` au moins une fois. Les octets invisibles (ANSI, `\r`) y apparaissent alors que le terminal les cache. Lance aussi `./btc input.txt 2>/dev/null` : si une ligne du sujet disparaît, c'est que tu as choisi un flux, et c'est un choix à pouvoir justifier.

## Finding 3 — Fichier en fins de ligne CRLF : chaque ligne devient « bad input »   [POLISH]

### What went wrong
`std::getline` coupe sur `\n` et laisse le `\r`. L'en-tête `date | value\r` ne correspond plus à `"date | value"`, et chaque valeur `3\r` échoue dans `isDecimal` :
```
Error: bad input => date | value^M
Error: bad input => 2011-01-03 | 3^M
```
Le `input.csv` officiel n'a pas pu être téléchargé (403), donc ce cas n'a pas été vérifié contre le vrai fichier. Le `data.csv` fourni est en LF (0 `\r`). Le risque existe si l'évaluateur édite le fichier sous un éditeur Windows ou le récupère avec des CRLF.

### Where
`BitcoinExchange.cpp:147-150` (lecture), `BitcoinExchange.cpp:61-71` (rejet)

### How to fix
Décide de ta politique et sache l'expliquer. Rejeter est cohérent avec ton choix sur les espaces finaux (`"3 "` refusé). Accepter voudrait dire retirer un `\r` final unique juste après `getline`. Les deux se défendent. Ce qui compte, c'est de connaître ce comportement avant qu'on te le montre.

### How to spot it next time
Génère un fichier d'entrée avec `printf 'a\r\nb\r\n'` et relis la sortie avec `cat -v`. Un `^M` en fin de ligne d'erreur est le symptôme exact. C'est le même piège qu'avec `get_next_line` sur un fichier Windows.

## Finding 4 — Cas numériques limites : `-0`, débordement, dossier en argument   [POLISH]

### What went wrong
- `2011-01-03 | -0` est accepté et affiché `2011-01-03 => -0 = -0`. Le zéro négatif IEEE passe `value < 0` (car `-0.0 < 0` est faux), puis `operator<<` l'affiche avec son signe.
- Un entier de 400 chiffres (ou 5 millions) donne `bad input` et non `too large a number`. `iss >> out` met le failbit en cas de dépassement, donc l'erreur sort par la branche « parse ». Même chose pour un négatif énorme, qui donne `bad input` au lieu de `not a positive number`.
- `./btc /tmp` (un dossier) : aucune sortie, aucune erreur, rc=0. Sur macOS, `ifstream` ouvre un dossier sans erreur, et c'est le premier `getline` qui échoue.

### Where
`BitcoinExchange.cpp:120` (`-0`), `BitcoinExchange.cpp:78-81` (débordement), `BitcoinExchange.cpp:145` (dossier)

### How to fix
Aucun de ces cas n'est dans la grille. Tu peux soit les traiter (normaliser `-0` en `0`, vérifier que le premier `getline` a réussi, faire la vérification de borne sur la chaîne avant la conversion), soit, au minimum, savoir les expliquer si l'évaluateur les tape. La grille dit *« You can modify this file with the values you want »*, et `-0` est le genre de valeur qu'un évaluateur aime essayer.

### How to spot it next time
Pour chaque test de signe (`< 0`), demande-toi « et `-0` ? ». Pour chaque conversion, demande-toi « et si ça déborde, par quelle branche je sors ? ». Pour chaque `open`, demande-toi « et si c'est un dossier ? ». Ce sont les trois questions de libft (`ft_atoi` sur `INT_MIN`, `open` sur un répertoire) appliquées ici.

## Finding 5 — Hygiène : macro `MAP`, code mort, fichier de notes   [POLISH]

### What went wrong
- `# define MAP std::map<std::string, double>` dans un header : une macro n'a pas de portée. Le nom `MAP` est remplacé dans chaque fichier qui inclut ce header, y compris dans du code qui n'a rien à voir. Le C++98 propose exactement l'outil fait pour ça : `typedef std::map<std::string, double> Rates;`, idéalement placé dans la classe.
- `F_WarnMsg`, `F_ErrExit` et `DBG` ne sont jamais utilisés. Le `try/catch` de `main` n'attrape en pratique que `std::bad_alloc`, puisque rien ne lance d'exception volontairement.
- `idees.txt` (notes de conception en français) est dans le dossier rendu.
- `loadDatabase` ne valide pas les dates de `data.csv`, et son message `Wrong input` n'a pas la même casse que `bad input`. `printDatabase` (mode debug) colore sans `RESET`.

### Where
`BitcoinExchange.hpp:7` ; `errors.hpp:17,20`, `utils.hpp:65-66` ; `ex00/idees.txt` ; `BitcoinExchange.cpp:101-105,157`

### How to fix
`typedef` à la place de la macro. Supprime ou assume le code mort. Retire `idees.txt` avant le push.

### How to spot it next time
Avant de rendre, lance `ls` dans le dossier de l'exercice et justifie chaque fichier. Pour chaque `#define` qui n'est pas un garde d'inclusion ou une constante, demande-toi si c'est un type (alors `typedef`) ou une valeur (alors `static const`). Le préprocesseur, c'est du C ; en C++ on le réserve à ce qu'on ne peut pas faire autrement.
